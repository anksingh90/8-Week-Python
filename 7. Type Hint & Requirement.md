## 1. Type Hints Fundamentals  

1. Type hints act as descriptive labels for your code. They tell developers and tools exactly what kind of data to expect for variables and return values.
2. Python does not enforce these rules when running your program. Instead, external checking tools like `mypy` read these hints to catch potential bugs early on.
3. Just like labels on moving boxes, type hints do not block the wrong items. They simply guide users and tools to prevent mistakes before things break.


### Example Code

```python
# Without type hints — reader has to guess
def calculate_total(price, quantity):
    return price * quantity

# With type hints — intent is explicit
def calculate_total(price: float, quantity: int) -> float:
    return price * quantity

# Variable annotations
student_name: str = "Aditi"
age: int = 18
gpa: float = 8.9
is_enrolled: bool = True

# Collection type hints (Python 3.9+)
subjects: list[str] = ["Math", "Physics", "Chemistry"]
scores: dict[str, int] = {"Math": 95, "Physics": 88}
coordinates: tuple[float, float] = (12.9, 77.5)

# A function returning nothing
def print_report(name: str) -> None:
    print(f"Report for {name}")
```

## 2. Type Hints — Optional, Union, Callable

- **Union** lets a variable accept multiple data types (like `int` or `str`), while Optional specifically means a variable can be a certain type or `None`.

- **Callable** is used when a parameter is a function itself, letting you define exactly what arguments that function accepts and what type of data it returns.

### Sample Code

```python
from typing import Optional, Union, Callable

# Optional[X] means "X or None"
def find_student(roll_number: int) -> Optional[str]:
    database = {101: "Aditi", 102: "Rohan"}
    return database.get(roll_number)  # Returns None if not found

# Union[X, Y] means "X or Y"
def format_price(value: Union[int, float]) -> str:
    return f"₹{value:.2f}"

# Modern shorthand (Python 3.10+) — same meaning as Union/Optional
def find_student_new(roll_number: int) -> str | None:
    # task for the method

def format_price_new(value: int | float) -> str:
    # task for the method

# Callable — describes a function signature as a type
def apply_discount(price: float, discount_fn: Callable[[float], float]) -> float:
    return discount_fn(price)

def ten_percent_off(price: float) -> float:
    return price * 0.9

print(apply_discount(1000.0, ten_percent_off))  # 900.0
```

### Why It Matters
`Optional` shows up constantly with databases — a lookup that might return nothing is exactly the SQLite pattern.

## 3. Code Quality — black, pylint, ruff, PEP8

- **PEP 8:** The official style rulebook for keeping Python code clean, consistent, and easy to read.

- **Black (The Formatter):** Automatically rewrites your code's layout—like spacing and quotes—so you don't have to fix the formatting yourself.

- **Pylint & Ruff (The Inspectors):** Tools that scan your script to warn you about hidden bugs and bad practices, leaving the actual fixing up to you.

### Annotated Code

```bash
# Install (inside your virtual environment)
pip install black pylint ruff

# black — auto-formats your file in place
black my_script.py

# Check what black WOULD change, without changing it
black --check --diff my_script.py

# pylint — reports a score out of 10 and lists issues
pylint my_script.py

# ruff — very fast linter, catches unused imports, bugs, style issues
ruff check my_script.py

# ruff can also auto-fix many issues
ruff check --fix my_script.py
```

### Common PEP 8 Rules You'll Actually Use

| Rule | Wrong | Right |
|---|---|---|
| Indentation | Tabs or 2 spaces | 4 spaces |
| Naming functions/variables | `myVariable`, `CalculateTotal` | `my_variable`, `calculate_total` |
| Naming classes | `student_record` | `StudentRecord` |
| Line length | 200-character line | Wrap at ~79–99 characters |
| Spacing around `=` in assignment | `x=5` | `x = 5` |
| No space in keyword args | `func(x = 5)` | `func(x=5)` |

## 4. Virtual Environments & requirements.txt

- A virtual environment is a private, isolated workspace for your project. It keeps installed packages separate from other projects to prevent version clashes.

- Think of your system's Python as a messy shared kitchen. A virtual environment gives you a personal kitchenette where your project's ingredients never get mixed up.

### Annotated Code

```bash
# Create a virtual environment named 'venv' in your project folder
python -m venv venv

# Activate it
source venv/bin/activate

# Your terminal prompt now shows (venv) — you're inside the isolated environment

# Install packages — they go into THIS environment only
pip install requests black pylint

# Freeze installed packages with exact versions into a file
pip freeze > requirements.txt

# requirements.txt now looks like:
# black==24.4.2
# pylint==3.2.0
# requests==2.32.3

# Anyone cloning your repo can recreate your exact environment:
pip install -r requirements.txt

# Deactivate when done
deactivate
```

1. **Create the Virtual Environment**
    - Run this once per project
    - Python to create a hidden folder named .venv to act as your isolated workspace.
    ```python  
    python -m venv .venv
    ```
2. **Activate the Environment**
    - Run this every time you start working
    - Before installing packages or running scripts, you must "turn on" the environment.
    ```python
    source .venv/bin/activate
    ```
3. **Install Your Packages**
    - Now that you are inside your private package
    ```python
    pip install black pylint ruff
    ```
4. **Save Your List (requirements.txt)**
    - Use command to save required packages
    ```python
    pip freeze > requirements.txt
    ```
5. **Recreate the Setup**
    - How to use the text file later
    ```python
    pip install -r requirements.txt
    ```

## 5. Git & GitHub — Commits, Branches, README

- Git is a local time-machine and tracker for your code. 
- GitHub is the cloud platform where you upload that tracked code to share, back up, or collaborate.

    - **README:** The instruction manual for your code.
    - **Commits:** Permanent snapshots of your work at a specific point in time.
    - **Branches:** Parallel, isolated versions of your code where you can safely build new features without breaking the main version.


### Annotated Code

```bash
# One-time setup (per machine)
git config --global user.name "Your Name"
git config --global user.email "you@example.com"

# Initialize a repo inside your project folder
git init

# Check status — what's changed, what's staged
git status

# Stage changes (prepare them to be committed)
git add filename.py
git add .          # stage everything

# Commit — save a snapshot with a message
git commit -m "Add deposit and withdraw methods to Account class"

# Connect to a GitHub repo you created online
git remote add origin git@github.com:yourusername/repo-name.git
git branch -M main
git push -u origin main

# After that, each session:
git add .
git commit -m "Clear, specific message about what changed"
git push

# Branching — work on a feature without touching main
git branch feature-grading
git checkout feature-grading
# ... make changes, commit ...
git checkout main
git merge feature-grading
```

### Commit Message Quality

| Bad | Good |
|---|---|
| `update` | `Fix KeyError when subject not found in dict` |
| `fix` | `Add SQLite persistence to Student class` |
| `done` | `Complete rank list feature sorted by percentage` |

### Minimal README Template

```markdown
# Project Name

One-sentence description of what this does.

## Tech Stack
- Python 3.12
- SQLite3

## How to Run
git clone https://github.com/yourusername/repo-name.git
cd repo-name
pip install -r requirements.txt
python main.py

## Features
- Feature 1
- Feature 2
```

### Why It Matters
This is the single most visible proof of your work to anyone hiring you. A dead GitHub with one commit called "first commit" is worse than no GitHub at all — it signals you don't build things consistently.

## 8. Weekend Mini-Project: Refactor Previous Project + GitHub Portfolio Setup

**Time:** 2–3 hours

### Steps
1. Pick your best project from Weeks 3–7 (e.g., Bank Account System, Shape Geometry System, Log File Analyzer)
2. Add type hints to every function and method
3. Add docstrings to every class and function

6. Create a GitHub repo named appropriately (see naming convention: lowercase, hyphens)

### Deliverable Checklist
- [ ] All functions/methods have type hints
- [ ] `black --check` passes with no changes needed
- [ ] `pylint` score improved and no critical warnings remain
- [ ] `requirements.txt` present (even if only listing formatting/lint tools used)

- [ ] Repo is Public
