## 1. Class & Object

**Definition:** A class is a user-defined template or blueprint used to create objects. It bundles data and behavior (methods) into a single logical unit.

```python
class Car:                              # class names are capitalized (PascalCase)
    def __init__(self, brand, model):   # __init__ runs automatically when an object is created
        self.brand = brand              # self binds data to the specific object being created
        self.model = model

obj = Car("Tata", "Tiago")              # creating an object of class Car
print(obj.brand)                        # Output: Tata
```

> **Note:** `obj.brand` is an attribute, not a method — no parentheses needed to access it.

You can create multiple objects, each holding its own independent set of values (e.g., before saving them to a database).

### 🧪 Practice — Class & Object

## 3. Inheritance

Inheritance lets one class (the **child**) reuse and extend the attributes and methods of another (the **parent**).

Here, `ElectricCar` inherits from `Car` and adds a new attribute.

```python
class Car:
    def __init__(self, brand, model):
        self.brand = brand
        self.model = model

    def car_name(self):
        return f"The name of the model is: {self.model}"


class ElectricCar(Car):                         # syntax: class Child(Parent)
    def __init__(self, brand, model, battery_size):
        super().__init__(brand, model)          # super() calls the parent's __init__
        self.battery_size = battery_size


obj = Car("Tata", "Tiago")
print(obj.car_name())

e_obj = ElectricCar("Tata", "E-Tiago", "50kWh")
print(e_obj.model)
print(e_obj.car_name())
```

## 4. Encapsulation

**Definition:** Restricting direct access to an object's internal data, exposing it only through controlled methods.

```python
class Car:
    def __init__(self, brand, model):
        self.__brand = brand            # double underscore prefix makes this "private"
        self.model = model

    def get_brand(self):                # public getter method for the private attribute
        return self.__brand

    def car_name(self):
        return f"The name of the model is: {self.model}"


obj = Car("Tata", "Tiago")
print(obj.brand)                        # AttributeError: 'Car' object has no attribute 'brand'
print(obj.get_brand())                  # Output: Tata
```

> **Convention:** Private attributes are accessed via `get_`/`set_` style methods rather than directly.

### 🧪 Practice — Encapsulation

**Mental model reminder:** Encapsulation is a bouncer at a club — nobody touches `self.__balance` directly, they go through the front door (`deposit()`, `withdraw()`). This matters *even more* once a database is involved, because you don't want raw, unvalidated data reaching your SQL.

        # log to failed_transactions table
        return False
    self.__balance -= amount
    # update accounts table
    return True

**Q4 — Encapsulated Password Storage (Never Store Plain Text)**

Create a `User` class where `set_password(self, raw_password)` hashes the password (use `hashlib.sha256`) before it ever touches `self.__password_hash` or the database — the raw password should never exist anywhere except briefly inside the method. import hashlib

class User:
    def __init__(self, username):
        self.username = username
        self.__password_hash = None

    def set_password(self, raw_password):
        self.__password_hash = hashlib.sha256(raw_password.encode()).hexdigest()
        # save username + password_hash to a users table

    def check_password(self, attempt):
        attempt_hash = hashlib.sha256(attempt.encode()).hexdigest()
        return attempt_hash == self.__password_hash

## 5. Polymorphism

**Definition:** The ability of different objects to respond to the same interface (method call) in their own way.

```python
class CreditCard:
    def process_payment(self, amount):
        return f"Charging ${amount} to Credit Card"

class Paytm:
    def process_payment(self, amount):
        return f"Redirecting ${amount} to Paytm gateway"

# Works with any object that has a process_payment method
def complete_checkout(payment_gateway, amount):
    print(payment_gateway.process_payment(amount))

complete_checkout(CreditCard(), 100)    # Output: Charging $100 to Credit Card
complete_checkout(Paytm(), 50)          # Output: Redirecting $50 to Paytm gateway
```

### 🧪 Practice — Polymorphism

**Mental model reminder:** Polymorphism is "same button, different machine." You press "process_payment" and each gateway does its own thing internally — including, here, logging itself to the database in its own way.

**Q3 — Abstract-Style Interface With a Shared Save Method**

Create a common parent using `abc.ABC` called `PaymentMethod` with an abstract method `process_payment(self, amount)`. Also give the parent a **concrete, non-abstract** method `log_to_db(self, amount, method_name)` that all children reuse. Each child implements `process_payment()` but calls `self.log_to_db(...)` internally — polymorphism (different `process_payment`) combined with shared inherited behavior (one `log_to_db`).

```python
from abc import ABC, abstractmethod

    @abstractmethod
    def process_payment(self, amount):
        pass

    def log_to_db(self, amount, method_name):
        # shared INSERT logic used by every subclass
        pass

class CreditCard(PaymentMethod):
    def process_payment(self, amount):
        # do credit-card-specific stuff
        self.log_to_db(amount, "credit_card")
```

## 6. Class Variables

Also called **static variables**. A class variable is defined directly inside the class body (outside any method) and is shared by **all** instances of that class — it exists in only one place in memory.

**Real-world use:** Storing data that should be common to every object of a class (e.g., a company name, a school name, a tax rate).

```python
class Student:
    school_name = "Bloom School"        # class variable — shared by all students

    def __init__(self, name):
        self.name = name                # instance variable — unique per student

# Accessing via the class name (recommended)
print(Student.school_name)              # Output: Bloom School

stu1 = Student("Ami")
stu2 = Student("Amy")

print(stu1.school_name)                 # Output: Bloom School
print(stu1.name)                        # Output: Ami
print(stu2.school_name)                 # Output: Bloom School
print(stu2.name)                        # Output: Amy
```

### 🧪 Practice — Class Variables

**Mental model reminder:** A class variable is one shared whiteboard that every object can read. An instance variable is each object's personal notebook. In a database, a class variable often maps to something like a config value or a running counter shared across every row you insert.

## 7. Mini-Project: Library Management System (OOP + SQLite3)

**Difficulty:** Intermediate-Advanced
**Time:** 3–4 hours
**Goal:** Combine every concept from this guide — Class & Object, `self` methods, Inheritance, Encapsulation, Polymorphism, and Class Variables — into one working, database-backed system.

This project deliberately mirrors the **Bank Account System** style project from Week 3, but is built around a library instead of a bank.

### Requirements

**1. Class & Object + Class Variables**
- A `Library` class where `library_name` is a **class variable** shared by everything (e.g., `"City Public Library"`)
- A class variable `total_books_registered = 0` tracked across every `Book` created

**2. Encapsulation**
- A `Book` class with a private `__isbn` (auto-generated, never changeable after creation)
- A private `__is_borrowed` flag, only changeable through `borrow()` / `return_book()` methods — never set directly

**3. Inheritance**
- A base class `Member` (`member_id`, `name`, `join_date`)
- A child class `PremiumMember(Member)` that adds `max_books_allowed = 10` (regular members get `max_books_allowed = 3`)
- Both should have their own database tables linked by `member_id`, following the pattern from Section 3

**4. Polymorphism**
- Both `Member` and `PremiumMember` implement a method `borrowing_limit_message(self)` that returns a different string depending on the class, without any `if isinstance(...)` check in the calling code

**5. Class Methods & `self`**
- `Book.save(self)` — self-saving method
- `Book.borrow(self, member)` — checks `member.max_books_allowed` against how many books that member currently has borrowed (query the database to count), then updates `__is_borrowed` and writes the change to the database
- `Book.return_book(self)` — reverses the borrow

### Database Schema (SQLite3)

```sql
CREATE TABLE books (
    isbn TEXT PRIMARY KEY,
    title TEXT,
    author TEXT,
    is_borrowed INTEGER DEFAULT 0,
    borrowed_by INTEGER
);

CREATE TABLE members (
    member_id INTEGER PRIMARY KEY AUTOINCREMENT,
    name TEXT,
    join_date TEXT
);

CREATE TABLE premium_members (
    member_id INTEGER PRIMARY KEY,
    max_books_allowed INTEGER DEFAULT 10,
    FOREIGN KEY (member_id) REFERENCES members(member_id)
);
```

## Quick Summary

| Concept | Core Idea | In This Practice |
|---|---|---|
| **Class & Object** | Blueprint vs. actual instance | Object → row, row → object (save/load) |
| **`self`** | Refers to the current object instance | Self-saving, self-updating, self-checking methods |
| **Inheritance** | Reuse parent class behavior in a child class | Table-per-subclass, cascading `super().save()` |
| **Encapsulation** | Hide internal data, expose via methods | Validated deposits, hashed passwords, read-only fields |
| **Polymorphism** | Same method name, different behavior per class | Shared `transactions` table, different DB effects per class |
| **Class Variable** | Shared value across all instances | Auto-increment IDs, shared config synced from the DB |
